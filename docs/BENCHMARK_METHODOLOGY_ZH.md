# 小模型工具调用与 Agent 控制边界 Benchmark 方法论

## 摘要

这套 benchmark 想回答的不是“一个模型会不会生成 function call”，而是：**当任务熵逐步升高时，小模型的可靠性在哪里开始断裂，以及哪些能力应该留给模型、哪些能力应该交给 harness。**

本文把工具型 Agent 的难度归纳为四个相乘因素：

> **歧义程度 × 动作空间 × 任务长度 × 分布偏移**

测试因此不以合法 JSON 或单步 exact match 为终点，而是建立一个可执行、可回放、可归因的闭环：模型选择工具并绑定参数，本地模拟器返回成功、空结果或错误，模型继续规划、恢复并主动停止，评分器最后从七个维度拆解表现。

核心判断是：

> **知识存储可以外置，知识使用能力不能完全外置；超小模型适合成为 Agent 的可验证器官，不适合在没有外部控制结构时直接充当整个大脑。**

## 1. 要研究的不是参数量，而是任务熵

“大模型一定比小模型强”过于粗糙。固定工具集、明确意图、参数完整、单轮执行和强约束输出，会把问题压缩到一个小模型也能解决的闭集分类与 slot filling 任务。真正的能力差异会在以下条件叠加后放大：

1. 用户表达含糊，甚至没有说明是否应该调用工具；
2. 工具数量增加，且多个工具描述相似；
3. 参数缺失，需要追问而不能猜测；
4. 当前调用依赖上一步返回的 ID、金额或状态；
5. 工具会超时、返回空结果、拒绝权限或报告业务错误；
6. 工具名、顺序、schema 或用户措辞偏离训练分布；
7. 任务需要十几步之后才完成，并要求模型自己判断停止。

因此，本方法论不把“模型大小”作为唯一自变量，而是主动控制四个难度乘数。

### 1.1 歧义程度

从参数齐全的直接命令，逐渐扩展到：

- 不应调用工具的知识问答；
- “先别发送”“只看不要创建”等否定指令；
- 缺少日期、收件人等必要参数；
- 用户只提供目标，没有指定中间动作；
- 工具报错后需要判断是重试、改参、换工具还是停止。

### 1.2 动作空间

从单工具扩展到：

- 功能相近的工具，例如天气预报与历史气候；
- 有副作用与无副作用的工具，例如查日历与新建日程；
- 多个 distractor；
- 动态召回后的 top-k 工具集合；
- 工具名匿名化后只依靠描述和 schema 选择。

### 1.3 任务长度

分别统计 0、1、2、3+ 次预期调用，并关注整条 episode 是否成功。假设每一步独立正确率是 `p`，连续 `h` 步全部正确的概率上限约为：

> `P(success) ≈ p^h`

例如单步正确率 95%，20 步全对概率仅约 36%；单步 99%，20 步后仍约 82%。单步 benchmark 只差几个百分点，长程 Agent 可能已经是“可用”和“不可用”的差别。

### 1.4 分布偏移

本套件通过三种 schema 条件建立最小对照：

- `original`：原始工具名与顺序；
- `shuffled`：确定性打乱工具列表，测量位置偏差；
- `aliased`：把工具名改成 `fn_01` 等中性名字，仅保留描述和参数 schema，测量对函数名先验的依赖。

数据还划分 core 与 OOD，并混合中英文、口语化表达、异常数值、同义改写和不同错误类型。

## 2. 三层能力模型

工具调用能力可以拆成三层，三层不应混为一个分数。

### 2.1 基座表征与知识使用

包括语言理解、语义表征、常识和对检索结果的理解。事实可以通过 RAG、搜索或数据库外置，但模型仍必须知道：

- 应该查什么；
- 如何把模糊需求改写成有效查询；
- 哪个结果与当前任务相关；
- 来源冲突时如何处理；
- 当前信息是否足够。

Fine-tuning 更像组织已有表征形成行为，不能从零制造一个缺失的世界模型。

### 2.2 工具策略

包括是否调用、工具选择和参数绑定。这一层最容易在封闭环境里被小模型压缩：

- intent router；
- tool retrieval；
- slot filling；
- 类型转换；
- JSON/grammar 约束输出。

### 2.3 长程控制

包括计划、状态保持、失败恢复和停止判断。它的误差会沿 horizon 累积，也是大小模型最容易拉开差距的部分。即使单步 function call 很漂亮，也不能据此推断模型可以稳定运行长程 Agent。

## 3. 七个评分维度

| 维度 | 核心问题 | 典型失败 |
|---|---|---|
| Relevance | 现在是否应该调用工具？ | 过度调用、缺参时擅自猜测 |
| Selection | 应该选择哪个工具？ | 混淆相似工具、调用不存在的工具 |
| Arguments | 参数是否忠实、完整且类型正确？ | 翻译不可变字符串、日期或金额错误 |
| Planning | 调用顺序与数据依赖是否正确？ | 未获得 customer ID 就查询订单 |
| State tracking | 是否真正使用工具结果？ | 最终答案丢失状态码或金额 |
| Recovery | 错误后能否采取有效新动作？ | 原样重试、修改无关字段、过早放弃 |
| Stopping | 成功或终止错误后能否停止？ | 重复发信、重复退款、无限循环 |

小模型通常可以在封闭场景中把 selection 和 arguments 训练得很好；更容易断裂的是 relevance、planning、state tracking、recovery 与 stopping。

## 4. 为什么必须是可执行环境

只检查一段 JSON 无法回答以下问题：

- 工具执行后模型有没有读返回值；
- 工具超时后是否重试；
- 空结果后是否改写查询；
- 售罄后是否选择下一个候选；
- 权限拒绝后是否停止；
- 有副作用的动作是否重复执行。

因此，每个 case 都包含确定性的本地工具 fixture。模拟器根据参数返回：

- 成功结果；
- 瞬时错误；
- 空结果；
- 业务错误；
- 终止错误。

所有副作用只在内存中模拟，不连接真实邮件、退款、订票、日历或订阅系统。状态在单个 case 内有效，不跨 case 泄漏。

## 5. 数据与评分设计

### 5.1 Case 结构

一个 episode 至少包含：

- 用户 prompt；
- 可见工具集合；
- 每个工具的 JSON Schema；
- 工具行为 fixture；
- 期望调用与参数；
- 合法调用顺序；
- 最终答案必须包含的事实；
- 最大调用数、禁止工具与错误恢复条件；
- 需要评分的能力维度。

### 5.2 参数忠实度

参数默认精确匹配，但业务上真正等价的表示可以显式声明 matcher：

- `$one_of`：例如“上海”和 `Shanghai`；
- `$contains_any`：自由文本检索命中任一关键词；
- `$contains_all`：查询或描述必须包含所有关键概念。

订单号、邮箱、金额、SKU、用户指定标题等不可变字段不能使用宽松 matcher。这个区分非常重要：城市名翻译可能是等价表示，但把用户要求的日程标题“模型评审”擅自改成 `Model Review` 是参数忠实度错误。

### 5.3 评分方式

- relevance：是否调用与 oracle 一致；
- selection：按带重复次数的 precision/recall F1；
- arguments：字段级部分分，并支持 exact/subset；
- planning：期望序列与真实轨迹的最长公共子序列比例；
- state tracking：最终回答是否包含工具返回的关键事实；
- recovery：是否经历错误、最终成功、达到最少调用数，以及是否有效改参；
- stopping：是否正常完成、是否有最终回答、是否超过最大调用数、是否触碰禁止工具。

案例 overall 是它声明的维度均值；`success` 只有在所有受测维度满分时才为真。报告同时提供：

- overall；
- perfect-case rate；
- 按维度分数；
- core/OOD；
- 0/1/2/3+ horizon；
- 停止原因；
- 完整调用 trace 和 token usage。

## 6. 两种输出协议

### 6.1 Native function calling

使用服务端标准 `tools` 与 `tool_calls` 字段，适合 vLLM、SGLang、llama.cpp 或商业 OpenAI-compatible endpoint。它测量模型、chat template 与 tool parser 组成的实际部署系统。

### 6.2 JSON protocol

对没有原生 function-call token 的小模型，把 schema 注入 system prompt，并约束输出为：

```json
{"tool_calls":[{"name":"tool_name","arguments":{}}]}
```

或：

```json
{"final":"answer"}
```

配合 grammar/JSON Schema 约束解码，可以把“格式容量”和“语义策略”分开。如果 JSON 约束显著提高 arguments，却没有提高 relevance 或 recovery，瓶颈就不在语法层。

## 7. 推荐实验协议

每个 checkpoint 至少运行：

| Run | Tool format | Schema | 研究问题 |
|---|---|---|---|
| A | native | original | 部署条件下的基础能力 |
| B | native | shuffled | 工具位置偏差 |
| C | native | aliased | 对函数名记忆的依赖 |
| D | constrained JSON | original | 去除语法错误后的语义上限 |

必须固定模型 checkpoint、量化、chat template、tool parser、context length、temperature、max tokens、随机种子和数据 commit。接口错误不能直接记为模型失败；应重跑对应 case，并在报告里留下替换原因。

## 8. 模型与 Harness 的分工

参数量不是硬定律，但可以形成工程上的粗略分层：

- **0.3–0.5B**：分类器、router、slot filling、固定格式转换器、极窄工具执行器；
- **1–3B**：在完善 harness 下承担领域 executor 和短链工具流程；
- **7B 以上**：更适合动态工具选择、歧义处理和多步规划；
- 更大模型的主要收益往往是泛化余量、容错和长程可靠性，而不是多几个离散技能。

对于小模型，推荐的系统结构是：

1. 小模型负责 intent、工具召回、参数抽取和局部决策；
2. 外部状态机负责流程、权限、幂等、重试预算和停止条件；
3. 只给模型动态召回后的 top-k 工具；
4. 用约束解码保证格式，把模型容量留给语义判断；
5. 训练数据大量加入“不该调用”、缺参追问、相似工具干扰、报错、空值和恢复轨迹；
6. 评测执行成功率、schema 扰动、OOD 改写和多轮恢复，而不只看 exact match。

## 9. 当前限制与后续路线

当前版本有 28 个双语 episode，适合快速回归，但还不足以形成公开排行榜。下一阶段应扩展：

- 10、30、100 个工具的动作空间；
- schema 描述改写、参数名改写和格式噪声；
- 自动用户模拟器，真正测试缺参多轮追问；
- 5、10、20 步 horizon；
- 幂等键、权限边界和高风险副作用；
- 开放搜索、冲突信息与不完整证据；
- 多 checkpoint、多量化、多 chat template 的置信区间；
- 多次采样与统计显著性，而不是单次 temperature 0。

## 结论

这套 benchmark 的目标不是证明“小模型不行”，而是找出它在什么条件下可以稳定成为 Agent 的一个组件，以及控制权从哪里开始必须交回外部系统或更强模型。

最终要比较的不是“会不会调用工具”，而是：

> **任务熵上升后，模型的执行成功率、泛化余量、错误恢复和停止可靠性崩得有多快。**
